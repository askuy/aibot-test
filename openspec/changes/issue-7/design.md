## Context

当前系统已具备文章浏览与用户身份认证能力，但缺乏将文章与用户关联保存的机制。用户在浏览过感兴趣的内容后，只能依赖浏览器历史或手动记录，无法在产品内快速回溯。

本次变更在现有用户体系与文章体系之间引入多对多的收藏关联，涉及后端 API 新增、数据库 schema 变更、前端交互新增三个维度，属于跨层变更，需在编码前明确技术选型与接口契约。

## Goals / Non-Goals

**Goals:**
- 用户可对文章执行收藏与取消收藏操作，并获得即时状态反馈
- 收藏状态在文章列表及详情页中对当前登录用户可见
- 提供"我的收藏"列表页，支持分页浏览已收藏文章
- 收藏数据持久化存储，刷新或重新登录后状态保持一致
- 收藏操作严格限定于已登录用户，未登录用户不可操作

**Non-Goals:**
- 收藏分组、标签或文件夹管理
- 收藏内容的离线缓存或本地同步
- 收藏数量统计展示（如文章被多少人收藏）
- 收藏的社交分享或公开展示
- 批量导入/导出收藏

## Decisions

**1. 数据存储：独立关联表而非嵌入用户文档**

新增 `user_favorites` 表，字段为 `(id, user_id, article_id, created_at)`，并在 `(user_id, article_id)` 上建唯一约束。

理由：收藏关系是典型的多对多结构，独立表使查询、删除、分页均可走索引，避免将无界数组嵌入用户或文章记录导致文档膨胀。替代方案（嵌入数组字段）在收藏量大时查询性能差，且无法利用数据库级唯一约束防止重复收藏。

**2. API 设计：RESTful 资源语义**

- `POST /articles/:id/favorite` — 收藏
- `DELETE /articles/:id/favorite` — 取消收藏
- `GET /users/me/favorites` — 获取当前用户收藏列表（分页）

理由：将收藏建模为文章的子资源，语义清晰，与现有路由风格一致。替代方案（单一 `PATCH /articles/:id` 携带 `favorited: true/false`）会将收藏状态混入文章更新语义，增加权限校验复杂度。

**3. 收藏状态注入：请求级查询而非全量预加载**

文章列表与详情接口在已登录状态下，通过 `LEFT JOIN user_favorites` 附加 `is_favorited` 字段；未登录时该字段始终为 `false`。

理由：无需维护额外缓存层，实现简单；列表接口已需查库，JOIN 代价可控。替代方案（前端单独请求收藏状态）会增加一次额外 RTT，用户体验较差。

**4. 并发安全：数据库唯一约束 + 幂等处理**

重复收藏时，数据库唯一约束触发冲突，服务层捕获后返回 `200 OK`（而非 `409`），保持接口幂等。取消收藏时，若记录不存在同样返回 `200 OK`。

理由：客户端可能因网络重试发起重复请求，幂等处理避免前端需要区分"已收藏"与"收藏成功"两种成功态。

## Risks / Trade-offs

**[列表查询性能下降]** 文章列表接口引入 LEFT JOIN 后，在高并发或数据量大时响应时间可能增加。
→ 缓解：在 `user_favorites(user_id, article_id)` 上建复合索引；列表接口限制分页大小（如最大 50 条）；后续可按需引入读缓存。

**[未登录用户的处理边界]** 未登录用户点击收藏按钮时，需前端拦截并引导登录，若前后端处理不一致会出现静默失败。
→ 缓解：后端在未携带有效 token 时统一返回 `401`；前端在渲染收藏按钮时依据登录态决定是否绑定操作或弹出登录引导。

**[数据库 schema 变更需迁移]** 新增表需要执行迁移脚本，部署窗口期间若新旧代码同时运行可能出现表不存在的错误。
→ 缓解：先部署迁移脚本（向前兼容），再发布应用代码；回滚时先回退应用代码，保留表结构（空表删除代价低，但需确认无脏数据）。

**[收藏列表与文章删除的一致性]** 若文章被删除，`user_favorites` 中的关联记录可能成为悬空引用。
→ 缓解：在 `article_id` 上设置外键级联删除（若数据库支持），或在文章删除逻辑中显式清理关联收藏记录。
