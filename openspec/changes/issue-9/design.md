## Context

本次变更为内容平台新增文章评论互动体系，是平台社区化建设的基础模块。当前平台已具备文章发布与用户认证机制，但缺少用户互动层。本设计基于现有认证系统，新增评论、回复、点赞三类核心能力。

**约束：**
- 评论回复仅支持一层嵌套（不支持无限递归），控制前端渲染复杂度
- 所有写操作（发评论、回复、点赞）依赖现有认证机制，不新增认证方案
- 初期不引入实时推送，采用分页拉取模式

## Goals / Non-Goals

**Goals:**
- 支持登录用户对文章发表顶级评论
- 支持对评论进行一层回复（parent_id 指向顶级评论）
- 支持对评论点赞与取消点赞，维护点赞数
- 评论列表按创建时间正序排列，支持分页
- 文章详情可附带评论总数统计

**Non-Goals:**
- 不支持多层嵌套回复（超过一层的楼中楼结构）
- 不支持评论的编辑与富文本格式
- 不支持评论举报、审核与屏蔽流程
- 不支持 WebSocket 实时推送新评论
- 不支持对回复本身进行点赞（仅顶级评论和一级回复均可点赞）
- 不涉及通知系统（被回复/点赞时的消息通知）

## Decisions

**1. 使用单表 + parent_id 表示评论与回复关系**

采用 `comments` 表中的 `parent_id` 字段区分顶级评论（`parent_id IS NULL`）和回复（`parent_id = 顶级评论 ID`）。

替代方案：独立的 `replies` 表。单表方案在仅一层嵌套的场景下查询更简单，无需跨表 JOIN，且未来如需扩展层级，迁移成本低于拆表方案。

**2. 点赞使用独立的 comment_likes 表（联合唯一索引防止重复）**

`comment_likes(user_id, comment_id)` 建联合唯一索引，通过数据库约束保证幂等性，避免应用层并发竞争。取消点赞为 DELETE 操作，点赞数通过聚合查询或冗余字段维护。

替代方案：在 `comments` 表中维护 `likes_count` 计数字段。冗余字段写性能更好，但在高并发下存在计数漂移风险；联合表方案数据一致性更强，初期流量下性能可接受。

**3. 回复列表随顶级评论一起返回（嵌套响应结构）**

`GET /articles/:id/comments` 返回顶级评论列表，每条评论附带其全部回复（`replies` 数组）。分页以顶级评论为单位。

替代方案：回复通过独立接口懒加载。单层嵌套场景下一次返回回复不会导致数据量过大，减少前端请求次数，简化交互逻辑。若单条评论回复量极大，可后续为回复单独加分页。

**4. 评论数统计采用 COUNT 查询 + 缓存，不在文章表冗余字段**

文章详情附带评论数时，通过 `SELECT COUNT(*) FROM comments WHERE article_id = ?` 获取，结合应用层缓存（TTL 短暂）减少数据库压力。

替代方案：文章表新增 `comment_count` 字段。冗余字段引入双写一致性问题，初期不引入此复杂性。

## Risks / Trade-offs

**[回复量过大导致单次响应体积膨胀]** → 当前设计回复随顶级评论全量返回，若某条评论回复数百条，单页数据量将显著增大。缓解措施：初期对回复数量设置上限展示（如最多返回前 20 条），超出时提供"查看全部回复"接口，后续按需扩展回复分页能力。

**[点赞高并发下的计数一致性]** → `comment_likes` 表保证不重复点赞，但若同时维护冗余计数字段，并发更新存在丢失更新风险。缓解措施：初期通过聚合查询获取点赞数，牺牲部分读性能换取一致性；如读压力上升，引入 Redis 计数器。

**[parent_id 未做评论层级校验]** → 若 parent_id 指向的评论本身已是一条回复，将形成超过一层的嵌套，违反设计约束。缓解措施：在创建回复的接口层校验 parent_id 对应评论的 parent_id 必须为 NULL，拒绝非法嵌套。

**[删除顶级评论时的孤儿回复]** → 若顶级评论被删除（未来支持删除功能时），其回复将成为孤儿数据。缓解措施：评论删除采用软删除（`deleted_at` 字段），或级联删除子回复；本期暂不实现删除，待删除功能设计时统一决策。
